# Research operations

[Blueprint §8.9](../../blueprint-v1.md#89-assignment-ledger-and-delegation-lifecycle) is authoritative. This is a Lead-invoked toolset, not a scheduler. Beads runs the backlog; the project ledger runs no agents and stores no duplicate task graph. The Lead calls the pinned `pi-subagents` runtime directly.

## Start a project

From the repository root, with Python 3.10+, Node 24, Git, Pi 1.6.0, `pi-subagents` 0.89.2, and `bd` 0.49.6 installed, prepare the project Python environment using approved package sources. Install both managed ledger validation and (for OKF) the writer's validator dependency:

```sh
python3 -m venv .tmp/research-ops-venv
. .tmp/research-ops-venv/bin/activate
python3 -m pip install -r tools/research-ops/requirements.txt -r .pi/agents/okf-writer/requirements.txt
```

Use that interpreter for initialization and the launcher. Bootstrap stores its path in the machine-local project binding for the Beads adapter; install the dependencies in that bound environment for an existing project. There is no automatic installer or fallback to unchecked managed snapshots.

```sh
python3 -B tools/research-ops/research.py init pilot \
  --question 'Does method B improve the frozen evaluation metric over A?' \
  --objective 'Compare A and B on a held-out set with paired observations'
python3 -B tools/research-ops/research.py preflight pilot
python3 -B tools/research-ops/research.py lead pilot --model 'provider/model'  # replace with your pinned model
```

The project receives its own `.beads/beads.db`, local `research-config.json`, managed `project-state.json`, and artifact tree. Init refuses an existing project directory; it never imports a root/child database. If interrupted during init, inspect the incomplete project before replacing or recovering it. Keep `.beads`, lock files, local machine paths, and secrets out of Git. Version evidence artifacts and the ledger. Back up the bound SQLite database separately using a consistent SQLite backup; do not copy only the live `.db` file out from under an active writer.

The default launcher starts **planning-only** Pi using built-in tools and the explicit Beads extension; child delegation and MCP are not loaded. Use a model available without extra provider extensions in that mode. For a qualifying deployment, `--enable-delegation` requires both the operator attestation described below and a pinned [Advisor consultation policy](#advisor-consultation-accounting). `--resume <pi-session-path-or-id>` changes only the conversation: reload the bound project ledger and reconcile before new work. Do not run multiple Lead host sessions against the same project. This repository tracks `.pi/` in a separate Git checkout; deploy both trees together.

## Beads tools inside the Lead session

- `bd_create`: supply an explicit full ID, title, and description. Use the prefix from `init`. If the receipt is lost, query that exact ID and compare fields before trying another mutation.
- `bd_get`: full ID only, including closed tasks. `bd_query`: required status scope (`active`, `all`, or one status), optional text, assignee/type/labels/priority range, limit 1–100. Native lexical search, not historical or semantic search.
- `bd_ready` / `bd_blocked`: operational discovery only. `bd_dependency`: add/remove/list planned blocking edges; `id` is the dependent and `prerequisite` is the blocker. Removing an edge is a Lead decision, not a substitute for the actual evidence pin.
- `bd_update` changes live task metadata/status. `bd_close` needs an exact durable acceptance or optional drop record (`recordId`) and a reason. A dropped task cannot release a dependent. `bd_reopen` corrects operational status; it does not reauthorize evidence.

No task Delete or generic CLI passthrough. The extension uses a shell-free argument vector, explicit database path, direct SQLite, no daemon or JSONL sync, bounded process time/output, and `model-only` Pi exposure. This prevents indirect Pi tool calls through the normal callable-tool registry. It does not confine an unrestricted shell or untrusted extension. Do not expose raw `bd`, project ledger writes, or this database to children in a live deployment.

## Ledger operations

```sh
STATE=research-projects/pilot/project-state.json
python3 -B tools/research-ops/ledger.py status "$STATE"
python3 -B tools/research-ops/ledger.py apply "$STATE" lifecycle start-scoping \
  --input - --op-id scope-001 --expected-revision 0 \
  --actor research-lead --reason 'Begin charter review' <<<'{}'
python3 -B tools/research-ops/ledger.py get "$STATE" <exact-record-id>
```

`status`, `next`, `progress`, `termination-check`, and `show <section> <state>` are read-only views. `status`/`next` distinguish project HOLD from `gate_holds` and expose any pending gate-HOLD checkpoint. A tool predicate or Candidate is not permission. Use `apply <state> <evidence|lifecycle> <action>` for managed writes. `--input` accepts a JSON file or `-` (stdin); each call needs the current revision and stable operation ID. An exact replay with the original parameters returns `replayed: true` and never permits launch. A changed operation with the same ID or a stale revision is refused. Legacy snapshots remain readable and their legacy `advance` only simulates a state; don't relabel legacy records as managed. Reconcile and import verified records explicitly before adopting existing projects.

`ledger.py validate <state>` checks the same structural schema and cross-record invariants used before managed reads, applies, and startup, and on newly initialized or changed managed snapshots before publication. The bundled [Draft 2020-12 schema](project-state.schema.json) uses local references only. Malformed state or a missing validator blocks use and leaves the file unchanged; do not edit history or discard records to pass. Shape validation does not verify referenced files, Git history, run outcomes, or scientific claims; evidence-consuming operations enforce their own checks.

### Task readiness and routing

Before meaningful work, retrieve the exact project task with `bd_get` and apply `evidence assess-task`. The assessment lives in its operation receipt; it does not duplicate Beads status, dependencies, or assignment history. Record a new assessment when the scope, pinned evidence, readiness, or route changes. This is separate from `mark-ready` (issued brief) and PLAN_GATE readiness (authorization for full evaluation).

| Field | What to supply |
|---|---|
| `beads_task_id`, `artifacts`, `next_step` | Exact Beads ID, a nonempty project-relative SHA-256 map of versioned evidence or a brief, and the concrete next step. Do not overwrite a pinned brief; version it. |
| `dimensions` | Exactly seven evidence-based narratives: `problem`, `information`, `methodology`, `competence`, `verification`, `risk`, `uncertainty`. No confidence score. |
| `classification` | `READY`, `INVESTIGATE` (a bounded check before reassessment), `CONSULT` (Advisor judgment), or `BLOCKED` (pause; escalate authority, resources, or essential input where needed). |
| `uncertainties` | Array of `{kind, issue, material, bounded_check}`; the seven kinds are factual, conceptual, methodological, technical, interpretive, strategic, and resource. Use `null` if no bounded check will resolve it. |
| `triggers` | Unique applicable trigger IDs (empty only if none): `unclear-question`, `unjustified-assumptions`, `material-method-choices`, `no-credible-evaluation`, `contradictory-evidence`, `hypothesis-undermined`, `repeated-conceptual-failure`, `substantial-interpretation`, `invalidating-scope-change`, `stage-review-gate`. A trigger or material uncertainty without a bounded check requires CONSULT or BLOCKED. |
| `routing` (READY only) | `{kind, fixed_role, handoff, required, assignee, reason}`. Use the matching fixed role and assignee for `kind: "fixed"` with `handoff: "eligible"`. Use `kind: "pool"` only if `fixed_role: null`, after checking all seven scopes and verifying an approved profile. Meaningful `kind: "lead"` work needs `assignee: null`, `required: false`, `handoff: "coupled"` or `"no-eligible-child"`, and a concrete reason. Unavailability does not make a fixed-role task pool work. |
| `gate` (stage review only) | `{gate, phase}` for `stage-review-gate`. The existing gate rubric, manifest checks, review, and route still apply. |

Use `get <state> <assessment-op-id>` for the exact receipt and `check-task <state> <assessment-op-id>` to recheck READY, current stage/cycle/plan, and evidence before relying on it. `status` and `next` expose the latest record and pending Advisor follow-ups. For mandatory advice, use the [versioned brief and checklist](consultation-brief.md) and authorized fresh Advisor call. Record the actual run using `record-consultation` with the `assessment_id`; a completed follow-up needs the result file in `evidence_ref`, a SHA-256 `artifacts` map pinning it, and `disposition` (`accepted`, `adapted`, or `declined`) with `rationale`. A timeout or an unrelated or reused run does not clear the obligation. Reassess after considering the answer. For a stage review, include the `assessment_id` on `gate-review` and use the legal gate route. If a linked gate submission becomes stale, withdraw it, reassess, and re-review; a later matching routed approval for that task/gate/phase in the same stage/cycle/plan can resolve the earlier referral.

Only Worker and pool assignment actions are mechanically guarded by READY routing; the Lead follows the same assessment discipline before direct work and fixed-role calls with their own protocols. The ledger does not establish task ownership, classify work from prose, authenticate child runs, enforce high-risk pass order, or check live child availability and resource limits. Use the prompt and approved runtime controls; an assessment is never a launch authorization.

### Evidence actions and payloads

| Action | Required payload and conditions |
|---|---|
| `issue` | `id` (revision ID), `assignment_id`, `beads_task_id`, `assessment_id` (current READY operation with the same task and route), one `assignee`, `mode` (`read`, `write`, `execute`), `scope`, `deliverable`, `criteria`, `exclusions`, pinned `source_versions` map, `read_paths`, `modify_paths`, `commands`, `external_actions`, `tools`, `attempt_limit`, `soft_seconds`, `hard_seconds`. Write/execute require full `base_revision` and commands or `verification_exemption`. Use `previous_revision` when revising; for an approved pool member, copy the assessment's fixed-roster scope rationale into `routing_reason`. |
| `pin-use` / `mark-ready` | Pin actual evidence by `id`, `consumer` (exact revision or review ID), `decision_id`, relative `output`, and `required` boolean. Readiness uses the revision `id` and recorded `basis`. |
| `reserve` | `id` (attempt), `revision_id`, `profile_ref` (operator-verified effective profile), and absolute `workspace` for write/execute. Recheck the linked Beads task and runtime resolution as Lead. Only the same uninterrupted call using the fresh receipt may submit once. |
| `attach-run`, `launch-unknown`, `prove-non-dispatch` | Attempt `id` and factual `evidence`; attach also needs the exact Pi `run_id`. If no reliable correlation exists after an interrupted submission, record `launch-unknown`; do not retry into uncertainty. |
| `hard-cutoff`, `observe-termination`, `record-no-result`, `reconcile-effects` | Attempt `id` and `evidence`. Record cutoff separately from termination. Reconcile effects only after observed termination; disposition is `clean`, `isolated`, or `integrated`. Termination means actual loss of mutation authority, not just a stop request. |
| `result` | `id`, echoed `assignment_id` / `revision_id` / `attempt_id`, `status`, `source_versions`, `deliverable`, `evidence_refs`, `gaps`. Write/execute add `affected_paths`, `deviations`, `follow_ups`, and `verification` keyed by the exact command with `{exit_code, output}` or `{not_run}`. Late results stay on the original attempt. |
| `decision` | `id`, `attempt_id`, `verdict` (`accepted` or `rejected`), `rationale`, exact `result_id` for acceptance, `supersedes` when correcting. Lead verifies independently. Unsupported, stale, partial, blocked, failed-check and late results cannot count as completion. |
| `record-availability` | `id`, `decision_id`, `artifacts` map (project-relative paths → SHA-256); write deliveries also need the integrated Git `checkpoint` containing those exact bytes. The adapter rechecks evidence before operational closure. |
| `drop-optional` | `id`, `revision_id`, `optional: true`, and recorded `gap`; all prior attempts must be reconciled. |

`issue`, `mark-ready`, and `reserve` recheck the assessment. Older briefs without an assessment remain readable and open attempts can still be reconciled. Before another launch, reconcile outstanding attempts, reassess the exact task, and issue a new revision linked to that assessment (no attempt-budget reset). An expired or superseded assessment likewise requires an updated brief before dispatch.

The ledger checks structural and causal consistency, Git ancestry and local hashes. It does **not** independently observe the Pi process, prove that a claimed check ran, choose a role, infer a dependency, or enforce filesystem/network boundaries. For an authorized dispatch, use the exact fresh `subagent` call with `context: "fresh"`, the verified `agent`, explicit model and `cwd` where applicable, an outer runtime limit, and the whole pinned brief including all three IDs. Preserve actual subagent receipts and status observations, not a reconstructed run reference. `complete`, child `SUCCESS`, Lead acceptance, integration, and Beads closure are distinct. If state disagrees with Beads, use exact IDs to reconcile and do not advance affected work. No cross-store transaction; don't issue another launch or blind close in response to a lost acknowledgment.

### Advisor consultation accounting

This accounts for Research Advisor calls, not specialist architect or Worker runs. The Lead still invokes Pi directly. **No consultation limits are set by default.** Before enabling delegation, an operator supplies a versioned JSON decision containing a unique `id`, an `operator` name, and `mandatory` and `exploratory` limits. Each lane has `calls` (project lifetime), `attempts_per_issue` (including the first attempt), and `per_call: {tokens, model_calls, seconds}` ceilings. Exploratory calls can be set to zero. Apply `lifecycle configure-consultations` with the exact two lane objects and `approval` (one project-relative path → SHA-256 pin to the operator's decision). Changing limits requires a new operator decision and reconciliation of outstanding calls; it does not reset prior charges. This establishes a recorded allowance, not an authenticated approval or an external provider quota.

1. **Reserve before calling.** After preparing the [decision brief](consultation-brief.md), apply `lifecycle reserve-consultation` with current `assessment_id`, a `brief` artifact hash map, requested `limits: {tokens, model_calls, seconds}`, and `pass` (`decision` or, for a high-risk required review, `evidence-first`). Set `purpose` to:
   - `gate`: supply the exact gate `manifest` and applicable `okf_check`. Uses the mandatory budget; retries are grouped by cycle, gate, and phase regardless of manifest edits.
   - `task-advice`: supply an unresolved non-gate `CONSULT` assessment. Uses the mandatory budget and keys retries to the Beads task, even if its assessment changes.
   - `exploratory`: supply a current nonmandatory assessment and `inputs: {question, assumptions, constraints, artifacts}`; use arrays of text for assumptions and constraints, and a project-relative hash map for cited evidence. Uses only the exploratory budget; retries are keyed to the Beads task. Keep the same Beads ID for the same issue; use separate tasks for independently scoped issues.
2. **Reconcile before retry.** The fresh reservation operation ID is the `attempt_id`. Only the same uninterrupted Lead invocation can submit it once under the approved runtime controls; replay or restart never authorizes launch. A pending reservation charges a slot and blocks another call on that issue. After verifying actual exit or non-dispatch, use `lifecycle settle-consultation` with `attempt_id`, `outcome` (`finished`, `failed`, `timed-out`, or `non-dispatched`), exact `run_id` when known, observed `usage: {tokens, model_calls, seconds}` (null for an unknown counter), and pinned `artifacts` for runtime/usage evidence. Use total tokens under the approved accounting convention, model requests, and whole elapsed seconds (round up). A timeout alone is not exit proof. Only verified non-dispatch returns a slot, and that receipt has no run ID or observed cost. Settlement works on HOLD without lifting it.
3. **Record and decide.** Use the same `attempt_id` on `record-consultation` or `gate-review`. Complete in-limit usage evidence is required to rely on a finished call. Missing counters are recorded as unknown, not zero; a failed, expired, or over-limit run does not count as usable advice or a verdict. An evidence-first pass is non-verdict advice; record it without the `assessment_id` on the advice record (the reservation already pins it) and use a separate charged decision call. Before depending on completed advice, record a pinned output and Lead disposition. When a required call cannot be made, pause the affected work or HOLD the gate; do not spend a different allowance or substitute cached advice. An observed overrun bars new reservations until a new operator decision; `status`/ `next` expose charges, unknown usage, observed usage, and outstanding reservations.

**Exploratory reuse only.** `lifecycle reuse-consultation` takes the accepted/adapted `consultation_id`, current `assessment_id`, identical `inputs`, and `rationale`. It checks the exact question, evidence hashes, assumptions, constraints, task and stage/cycle/plan, source output, original brief and runtime observation. Reuse logs a reference without charging a call, creating a child result, or satisfying a mandatory review. For subsequent empirical checks, `lifecycle record-advice-check` takes `consultation_id`, `finding` (`supported`, `contradicted`, or `inconclusive`), `rationale`, and hashes of independent observation artifacts. Recorded contradiction disallows reuse; the ledger does not judge the check's scientific validity.

Older unconfigured ledgers and previous reviews remain readable; historical calls are not retroactively metered or eligible for reuse. The configured launcher requires current policy evidence in addition to the runtime attestation. The ledger checks declared limits and recorded observations, not actual spend or the truth of the observations. External quota, provider/tool controls, and verified runtime accounting still have to be qualified before live use.

### Gate actions

Use `start-scoping`, `start-planning` (`charter_ref`), `objective` (`id`, `status`, `evidence_refs`), and `progress` (`verdict`, `credible_lever`, `evidence_refs`). Store Advisor/architect advice separately with `record-consultation` (`id`, `agent`, `run_id`, `status`, `evidence_ref`). Use `record-blocker` (`id`, `description`, `status`), `open-hold` (`reason`), `resolve-hold` (`resolution`), or `suspend-held` (`status_report` and confirmed blocker or `director_decision`) as applicable.

New projects use zero cycles during creation and scoping; `outer_cycle: 1` names the upcoming cycle. `start-planning` charges cycle 1 in the same managed write and returns `charged_cycle: 1`. Replaying the operation does not charge again, and a failed PLAN_GATE does not refund the charge. Existing snapshots that were already charged at initialization do not charge again on `start-planning`.

**Inner attempts.** After protocol approval, apply `begin-inner-attempt` with `{}` **before making changes** in the cycle workspace. This pins the current Git `HEAD` as the base and reserves one pending attempt without charging. Start from a committed base and a Git-clean project `src/`; accepted Worker deliveries still follow their separate verification and acceptance checks. Only one inner attempt can be pending. `status` reports its `start_op_id` and `base_revision` for reconciliation on resume; managed gate reviews and routes wait until settlement.

To settle, supply `{"start_op_id": "<begin op ID>", "checkpoint": "<full current HEAD hash>"}` and use `--reason` to describe the observed integration or interruption. Choose the action based on reconciled effects:

- `record-inner-integration` verifies committed project `src/` changes on the first-parent history from the pinned base to the current workspace `HEAD`, records the integration commit IDs, and charges once, even if evaluation never starts. Workspace-only edits, side-branch-only commits, and commits outside this project's `src/` do not count. An integrated change followed by a revert still counts as a change during the attempt.
- `record-no-change-interruption` records the interruption without charging only if that history has no integrated implementation changes and `src/` is Git-clean. Reconcile outstanding workspace writers or unaccepted edits first. Git checks are not proof that ignored files or external effects are absent; the Lead still has to reconcile those separately.

Both settlements can record facts on HOLD without lifting it. If work is terminally suspended before effects are known, preserve the pending record and explain the unknowns in the status report. Never re-pin the base to hide uncertain effects or rewrite history. These checks govern the ledger path, not direct changes made outside it. Historical counts from the earlier immediate-charge behavior are preserved, not reclassified as Git-verified.

Create a phase-specific, versioned artifact manifest using `checks.py manifest` (relative file paths). `checks.py validate-verdict` and `checks.py verdict-still-covers` check shape, phase, target, and hashes. Supply exact review `id`, `gate`, `phase`, `advisor_run_id`, `manifest`, and §4.4 `verdict` JSON or `failure` to lifecycle `gate-review`. `gate-route` requires that review `id` and a legal `route`; a gate HOLD needs a reason and a terminal stop needs a pinned `status_report` file. A failed verdict or selected gate HOLD parks that dependency, checkpoints the review, and leaves the project active; unrelated assessed work may continue. That is distinct from project HOLD (`open-hold`), which prevents dispatch. Before continuing, check the exact Beads task and its transitive dependencies; do not issue or launch work blocked by the held gate. Beads remains the dependency authority—the project ledger does not infer or mirror its graph, so this scoping depends on the Lead's verified task lookup and is not a host-level sandbox. After collecting hashed triage evidence, `lifecycle resolve-gate-hold` with `id`, `resolution`, and `artifacts` permits a bounded re-review of that gate/phase; it does not authorize a route. A further review is refused until the hold is resolved. Only a designated valid verdict and its Git-checkpointed route advance the stage. Use `withdraw-stale-review` for an unrouted review that no longer matches, then re-review. Protocol, readiness, complete/diagnosis-only exit, cycle, and report are distinct. `replan` requires `proposed_route: "replan"`, `next_plan`, and `replan_rationale` in the reviewed cycle manifest. Only consuming a current `approve/replan` charges the next cycle.

#### Required artifact roles

Build each gate manifest with `--artifact-roles ROLE_MAP.json`, a JSON object mapping the role names below to **distinct, nonempty project-relative files**. The builder hashes these files automatically; add supporting artifacts as positional paths. A required package of multiple files can use a versioned index for its role; pin the primary evidence in the gate manifest as well. Do not use placeholders. Where an item is genuinely inapplicable, record why; incomplete evaluation goes to diagnosis, not to complete exit.

| Phase | Required roles |
|---|---|
| `protocol` | `charter`, `literature-review`, `hypotheses`, `methodology`, `evaluation-plan`, `roadmap`. The charter must be the active ledger charter. |
| `readiness` | `dependency-lock`, `environment`, `dataset-manifest`, `experiment-config`, `test-sources`, `reproduction`, `implementation-notes`, in addition to the tested baseline and passing logs below. |
| `complete` | `config-snapshot`, `raw-results`, `execution-metadata`, `analysis-scripts`, `metrics-and-figures`, `ablations`, `failure-taxonomy`, `attempt-notes`. |
| `diagnosis` | `diagnosis-note`. Pass `--phase-evidence` with `{"diagnosis":{"reason":"requires-plan-change","gaps":["<specific gap>"],"rationale":"<why completion is unavailable>"}}`. The other reason, `attempt-budget-exhausted`, is valid only at the recorded inner-attempt limit. This package can authorize diagnosis, never a success claim or report route. |
| `cycle` | `hypothesis-assessment`, `threats-to-validity`, `limitation-diagnosis`, `progress-verdict`, `cycle-decision`. |
| `report` | `report`, `claim-evidence-matrix`, `reproduction`, `references`, `final-manifest`, `verification`. |

For `cycle`, supply `--phase-evidence` containing `proposed_route` (`hold`, `stop`, `report`, or `replan`); include `next_plan` and `replan_rationale` for replan. Pin a versioned `cycle-decision` JSON proposal with `id`, `cycle`, `plan_version`, those same proposal fields, `rationale`, and `evidence_refs` (nonempty list of other hashed paths). Do not include `selected_route` in the proposal. A forward route on approval must match the proposal and the legal route under the current predicates. The selected route is recorded separately in the committed `cycle-decision.json` described below, preserving the reviewed proposal unchanged.

For `report`, `final-manifest` is a JSON object with an `artifacts` hash map that includes the report, claim-evidence matrix, reproduction instructions, and references. Other entries must also be pinned in the gate manifest. No self-references or reference to the verification file. The independent `verification` JSON names `verifier` and `method`, and its `artifacts` map pins exactly those four required files plus the final manifest. The Lead still checks independence, resolves required findings, and verifies claim support. Mechanical checks do not establish those judgments.

Historical reviews missing role bindings remain readable, but do not authorize new reliance. Reconcile affected work and obtain a review of a compliant package; if the current stage cannot accept the needed review, HOLD for explicit recovery instead of editing the historical review.

**Protocol and readiness.** The protocol manifest lists unique `required_tests` IDs (one `--required-test ID` per test when building it). Build a readiness manifest with `--readiness-evidence` and a JSON file of this shape, listing the baseline and output files among the manifest paths:

```json
{
  "protocol_review": "protocol-review-id",
  "revision": "<full tested Git revision>",
  "baseline": ["src/methods/baseline.py"],
  "tests": {"unit": {"exit_code": 0, "output": "evidence/unit-attempt-1.log"}}
}
```

Readiness targets the latest routed protocol approval and requires matching test IDs, pinned output logs, and baseline bytes from the tested commit. Later history-only checkpoints (e.g. a ledger commit) are fine; committed or dirty changes under `src/` are not. These are checks on recorded observations, not independent test execution. Historical reviews remain readable, but older approvals without these fields are not full-evaluation authorization; reconcile or diagnose and obtain a compliant review rather than inferring the missing evidence.

**In-plan rework and reuse.** `return-to-implementation` takes a `reason` and hashed `artifacts` explaining in-plan rework or stale coverage. It does not charge or approve an inner attempt by itself. Ordinarily submit a fresh readiness review. For the §5.3 exception, `reuse-readiness` takes the original `review_id`, a new `manifest`, and `proof: {"diff": "<artifact>", "unchanged": {"interfaces": "<evidence artifact>", "contracts": "<evidence artifact>", "validity_assumptions": "<evidence artifact>"}}`. Capture the exact patch with `checks.py readiness-diff <project-root> <approved-revision> <tested-revision>`. Hash the patch, the evidence for unchanged assumptions, new passing per-attempt logs, and the current baseline. Retain the original non-baseline evidence and its role-to-file bindings, and account for integrated changes. Approval reuse does not create a new Advisor verdict, bypass required gate review, or approve a protocol change. If the Lead cannot establish unchanged assumptions, obtain a fresh readiness verdict; if the protocol needs to change, use the diagnosis-only route.

### Git checkpoints for gate decisions

A verdict is not yet a route. Before `gate-route`, `reuse-readiness`, or the initial `start-planning`, prepare and commit an exact transition record. These commands do not create commits or push.

1. Pick the operation ID and proposed payload as for `apply`, but omit `checkpoint`. Run `ledger.py checkpoint-plan <state> <action> --op-id <id> --input <payload.json>`. Save its `decision` object at the returned project-relative `decision_path`. Do not commit the wrapper. This command describes the proposed transition; it does not decide if the route is legal. For any cycle route also supply `rationale`; for a `stop` route, `status_report` names the project-relative status-report file, not inline prose.
2. The checkpoint record is machine-owned JSON in the hub. For an OKF-dependent route or reuse, publish a validated snapshot including this new JSON before committing (an unchanged Markdown stage is sufficient), then run a fresh `check-okf-gate` for the **same** reviewed manifest. Use that newer receipt as `okf_check` on `apply`. If reviewed artifacts changed rather than just the hub's unreviewed decision record, obtain a new review. Any other ledger write after the commit makes its state pin stale.
3. Commit the current `project-state.json`, the decision JSON, the required role files, and use the returned `git_subject` (it may have a comma and more detail). For initial planning, commit the active charter. Readiness also checkpoints the baseline and test logs; reuse checkpoints the diff and unchanged-assumption proof. An applicable OKF checkpoint must contain the exact hub tree and pinned service-result files. Supporting large data can remain off Git: keep it pinned in the reviewed manifest and use a committed versioned role index rather than committing a large raw result as a role file.
4. Call `apply` with the same operation ID, current expected revision, and the full current `git rev-parse HEAD` as `checkpoint`. The ledger checks legal routing again, first-parent continuity from its last checkpoint, and exact committed bytes. A committed proposal becomes a consumed decision only when the receipt is persisted. A cycle decision record links the reviewed proposal and verdict to the selected route, rationale, next cycle and charge. Commit the resulting ledger receipt promptly; the next guarded route must checkpoint its own exact pre-transition state as well.

If interrupted after committing but before `apply`, read the canonical ledger first. If the receipt is absent, the exact committed pre-transition state and decision allow the same action to be verified again (with the matching OKF receipt when applicable). If the receipt is present, exact replay returns it without any extra charge. Do not reset or rewrite published history to recover. The ancestry guard assumes the live ledger still carries its receipts; it cannot detect rollback of both the Git history and the ledger together.

A `block` or unusable verdict puts its dependent gate on HOLD immediately, without waiting for Git. Before any other managed dispatch or gate review, use the same checkpoint procedure for `checkpoint-gate-hold` with the review `id`. That checkpoint binds the recorded failure/HOLD and does not require possibly missing submission artifacts. It does not resolve the gate HOLD or advance the stage. After triage, `resolve-gate-hold` records the evidence and permits a bounded re-review; a valid new verdict still needs its own checkpointed route. This gate-level HOLD leaves project status active so unrelated eligible tasks can continue. Use `open-hold` only for a project-wide safety, authority, or resource pause. Historical receipts without these fields remain readable and are not retroactively labelled checkpointed.

### Director decisions, escalation, and stops

Communication is direct and chat-first. The ledger records observations; it does not send messages, identify the speaker, infer consent, monitor a session, enforce an external quota, or terminate children. Use the same decision ID in chat, the hub, and ledger operations below. Pin versioned, minimally necessary observations in `artifacts` (project-relative SHA-256 map outside the hub, staging, and live ledger); do not retain secrets or unnecessary transcript text.

| Lifecycle action | Required payload and effect |
|---|---|
| `record-director-message` | `id`, `tag`, `delivery` (`sent` if observed or `pending`), `artifacts`. For `FYI`, add `summary` and the Lead-owned `next_step`; it creates no hold. For `DECISION-REQUIRED`, add `ask`, `why_now`, `without_reply`, `trigger` (`charter`, `authority`, `resources`, `essential-information`, or `exhausted-recovery`), `scope`, `options`, and `recommendation`. Use a `deadline` only for a real cutoff. |
| `record-director-delivery` | `id`, observed `status` (`sent` / `pending`), and `artifacts` to reconcile a posting gap. Record a pending gap if delivery is unknown; never infer receipt. |
| `record-director-reply` | `id`, `classification`, `artifacts`. For `ambiguous`, `question`, or `preference`, add `next_step` (a focused question for ambiguity). These do not authorize work. For `authorization`, name the exact `option` and record a `readback` of its effects; the decision stays open until filed. |
| `file-director-record` | `id`, `publication_id` from the exact current managed OKF publication. Filing verifies the decision version, standing brief, and index links. A clear reply closes only after this step. Writer outage or a stale/unindexed filing does not release dependent work. |
| `request-director-stop` | `id`, `reason`. Park the project immediately even if the hub or evidence is unavailable. Honor the actual stop in-session before polishing records. Reconcile the instruction using the `stop` option on `record-director-reply`, then file it under the same ID. |
| `record-director-stop-reconciliation` | `id`, `summary`, and `artifacts` of observed affected-run exit/non-dispatch and effect reconciliation after an authorized project stop. Refused while any managed Worker, Advisor, hub publication, or inner attempt remains unresolved. This is separate from the stop request and from terminal status. |

Use `scope: {"kind":"project"}` for a project-wide authority boundary (including charter changes, resources, and project stop), or `{"kind":"tasks","task_ids":["<exact-beads-id>"]}` with sorted unique IDs. Task-scoped requests block that work, not independent in-stage work. Managed gate progression parks while any governed request is open, since it cannot infer that a gate is independent of those tasks. A new scoped authorization requires a fresh READY assessment before redispatch; stale unrouted gate reviews require a fresh submission. Write `options` as `{"option-id":{"consequence":"...","outcome":"narrow"}}`; outcomes are `resume-within-authority`, `narrow`, `authorize-resources` (resource requests only), or `stop` (project scope). `recommendation` names `option`, `basis`, and `change_if`. To replace an unsettled request add `supersedes` with its exact ID and keep its scope and trigger. File both versions; do not overwrite the earlier record.

**File and refresh.** `get <state> <decision-id>` exposes the current record marker. Use that exact marker on its own line in `change-and-progress-logs/decisions/<id>.md`. Publish it with `director-brief.md` and the root `index.md` under the managed OKF protocol. The index links both files; the brief links the decision. Include `status` → `director.brief_marker` on its own line in the dated brief. The marker checks known ledger context, not the accuracy of the prose. At CYCLE_GATE and REPORT_GATE a stale, missing, or unindexed brief blocks the managed OKF check. Refresh when decisions, material status, or conclusions change; state the as-of time/stage, what changed, decision needed or none, next checkpoint, and source/time/coverage of spend. Disclose stale or missing facts when answering the Director. On HOLD or after terminal status, new staging is limited to Director records, brief, and index; it does not authorize child launch or resume research.

**Resume or suspend.** A filed reply does not lift a project HOLD. For a resource HOLD, `resolve-hold` also needs the exact list in `status` → `director.resources_to_reconcile` as `resource_decisions`, plus `reconciliation_artifacts` pinning the verified narrowing or effective controls. Do not resume on a stop. `suspend-held` requires a pinned project-relative `status_report` and `artifacts`, plus a confirmed unresolvable blocker or an exact, filed project stop ID as `director_decision`. A resource hold itself never authorizes suspension. Report unresolved work explicitly if exit/effects have not been reconciled; a SUSPENDED receipt is not proof that processes stopped.

### Managed OKF publication and recovery

The launcher holds an exclusive project lock for the lifetime of the bound Lead process. The canonical `project-state.json` ledger permits one pending hub request at a time, and the ledger CLI serializes live file replacements. The writer edits a staged copy; only the managed publisher applies those Markdown bytes to the live hub. These are cooperative local controls, not a sandbox for Pi tools, raw shell writes, or unbound sessions.

1. Apply `lifecycle begin-okf-publication` with `paths` (authorized bundle-relative Markdown paths, including any index/log changes) and `request_artifacts` (project-relative path → SHA-256 pins to the exact writing brief). The operation ID is the request ID. The receipt pins the ledger revision and live bundle bytes and gives a fresh `staging` path under `runtime/okf-staging/`. Copy the **complete** live bundle there without links, then give the writer only the staging root, exact request ID, allowed paths, and pinned brief. The writer must not write the live hub. The reservation is not a dispatch authorization.
2. After verifying writer exit and matching its result to the request, apply `prepare-okf-publication` with `request_id`, project-relative `writer_result`, and `writer_artifacts` pinning that exact result. Keep briefs, result JSON, and recovery evidence outside both hub and staging. The staged `committed` result means only that changes were applied to the stage; the CLI validates the complete stage, checks the exact declared file diff, and persists all target hashes before live writes. Machine-owned JSON is not part of the writer's scope. A no-change stage is allowed with empty result path lists (e.g., to checkpoint existing hub content or separately updated machine-owned JSON). No-op publication cannot adopt Markdown drift since the last checkpoint.
3. Apply `publish-okf` with `request_id`. The publisher validates the pinned stage and result again, replaces only allowed files, rechecks the live hub, and persists a receipt. This is a filesystem/ledger checkpoint, **not** a Git commit or a multi-file atomic rename; the Lead records the required Git checkpoint before an applicable gate route. Keep the staged copy unchanged until publication settles. After verifying the receipt, retain or archive stage material as needed; never reuse the request or staging path.
4. **After interruption**, inspect `status` or `next` and the exact request with `get`. Do not relaunch merely because the result or receipt is absent. For a prepared request, reapply `publish-okf` only after reconciling the staged writer and restoring missing pins. It resumes if every live file still matches either its exact base or target bytes. Unexpected bytes, changed staging, or a failed validator leave the request pending and gate progression blocked. If abandoning the request, confirm actual writer exit or non-dispatch, restore and verify the exact base if needed under separate recovery authority, and apply `abort-okf-publication` with `request_id`, `writer_state` (`terminated` or `not-dispatched`), and pinned `recovery_artifacts`. Timeout alone is not exit proof, and abort cannot clear an unrestored partial publication. Reconciliation does not lift HOLD.

**Required OKF precheck.** `CYCLE_GATE` and `REPORT_GATE` require a passing managed check. For other writer-dependent gate inputs set `okf_required: true` in the manifest; set `okf_reader_required: true` where a reader result is required. After successful managed publication and service reconciliation, apply `check-okf-gate` with the exact `manifest`, `publication_id` and `hub_sha256` from the current publication receipt, project-relative `writer_result` and applicable `reader_result` paths, and `service_artifacts` mapping those paths to SHA-256. The writer pin must match the publication receipt. `checks.py okf-hub-snapshot <project-root>` is an inspection of current bytes, not a substitute for publication. The action runs the existing bundle and envelope validators and index checks (install the writer's PyYAML requirement separately).

Pass the operation ID as `okf_check` on `gate-review` (or `reuse-readiness` if applicable). Routing rechecks the receipt's exact manifest and cycle, publication checkpoint, hub contents, envelopes, and validator versions. If the receipt is stale, reconcile and supply a fresh check for the same manifest; changes to reviewed artifacts still require a fresh review. An omitted or failed required check cannot authorize advancement. When `okf_reader_required` is true, the pinned reader result must be `sufficient`, contain evidence entries, identify existing bundle files, and include `revision.bundle_sha256` matching the exact checked hub snapshot. `partial`, `insufficient`, empty evidence, stale, or unspecified-snapshot results cannot satisfy that manifest. Optional retrieval may be partial and its gaps remain visible; declare sufficiency a gate dependency only when required. `checks.py okf-gate-precheck` remains an inspection command, not a managed receipt. Previous prechecks without publication receipts stay readable but do not authorize a new route. Receipts do not authenticate an agent run, its conclusions, or confinement.

`checks.py freshness-flags` checks an explicitly extracted provenance snapshot against the ledger and `stale_after`; it does not infer freshness from Markdown prose. `analyze.py` is a reference paired-evaluation helper: version and freeze the config/input hashes, record raw `example_id,baseline,candidate` CSV, and emit JSON analysis or a Markdown **draft**, not a final report or Advisor verdict.

## Deployment exit checks (not satisfied by fixture tests)

`preflight` verifies installed pins, bindings, and file fingerprints, not actual role resolution. In a disposable, credentialed Pi deployment with the operator's approved provider and confinement setup:

Run each fixed role with explicit `fresh` context against trivial disposable inputs. Capture the actual run ID, definition source, requested and resolved provider/model, override source, executed tool list/reachable tools, and the final result. Keep actual output and inspection files in the project.
2. Probe denied paths, commands, delegation edges, `codemode` access, fresh-context exclusions, hard-cutoff process exit, and correlation of an exact prelaunch attempt after restart. Verify the Lead lock and stage-only OKF writer isolation in the actual runtime; exercise interrupted staging and live publication recovery with real run/exit evidence. Run the Worker writer pilot and interrupted-close recovery. Refuse release when any mandatory probe cannot be verified; an assertion of attempted dispatch is not proof. Run a separate approved read-only pool pilot; recheck actual pool profile and its full capabilities at every call. `checks.py check-pool-profile APPROVAL OBSERVATION` compares the operator's `{operator, profile}` approval to the actual observed resolution. A profile contains `name`, `definition_sha256`, exact `model`, `override_source`, and explicit `tools`, `indirect_tools`, and `model_endpoints` lists. This comparison is not discovery or sandbox enforcement. No default pool is authorized.
3. Save `runtime/attestation.json` with `operator`, `fingerprints` (from `preflight`), and `roles` keyed by the seven names. Each role includes `definition`, `run_id`, `requested_model` and `resolved_model` as exact `provider/model`, `override_source`, `completed: true`, `fresh_context: true`, `effective_tools`, and `artifacts` as a nonempty project-relative SHA-256 map. `probes` is a map from `writer_confinement`, `worker_nested_edges`, `codemode_boundary`, `exact_restart_correlation`, `hard_cutoff_and_process_exit`, `fresh_context_and_models`, and `okf_publication_recovery` to equivalent evidence maps. `smoke-roster <project>` **validates recorded observations; it does not run paid jobs or certify their truth.** Inspect the actual artifacts before attesting. Relaunch after material runtime changes only after re-verification.
4. Establish provider/API and compute quotas outside the local ledger, independent monitoring and interrupt authority, and retained runtime evidence. This toolset accounts for cycles, reviews and attempts, not external compute charges. For real scientific evaluation, the Director supplies the research question and approved resource budget; compare repeated runs and preserve negative/inconclusive findings.
